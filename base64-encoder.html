Why it matters

Why UTF-8 safety and URL-safe output decide whether your payload survives

Two failure modes account for almost every Base64 bug in production, and both are invisible until a user in a non-English market hits them.

The first is Unicode corruption. The browser's btoa() accepts only "binary strings" — characters in the range 0 to 255. Pass it a string containing an emoji or a Chinese character and it throws an InvalidCharacterError; pass it a string that merely looks fine in Latin-1 and you get silently mangled output. The fix is to encode your text to UTF-8 bytes first with TextEncoder, then Base64 the bytes. Decoding runs the same pipeline in reverse through TextDecoder. That single decision is why this tool round-trips Uber, naive, Tokyo and an emoji without complaint, while older generators turn them into question marks or throw a "URI malformed" error.

The second failure mode is alphabet mismatch. Standard Base64 draws on A-Z, a-z, 0-9, + and /, with = as padding. In a URL or a filename, + is read as a space, / looks like a path separator, and = is a query delimiter. RFC 4648 section 5 defines a URL-safe variant that substitutes - and _ and drops the padding entirely — which is exactly what JWT segments, OAuth state parameters and signed URLs use. Flip the toggle and this tool emits that variant; the decoder accepts either form automatically, so you never have to guess which one you are holding.

Developer notes

Base64 rules that age well in production

Remember what Base64 is not: it is not encryption and it is not compression. The output is roughly 33% larger than the input, and anyone holding the string can decode it in one line of JavaScript. Never use it to protect a secret. Its value is transport integrity — moving bytes through a text-only channel without loss.

When you embed a data URI, keep an eye on the cost. A base64 image is about a third bigger than the file it came from, it cannot be cached independently of the page that carries it, and it blocks parsing while it loads. Inline the small, critical assets — a logo, a spinner, an icon — and keep large photographs as separate, cacheable files. The tool's byte counter exists so you can see that trade-off in numbers before you commit to it.

Finally, match the variant to the consumer. Use standard Base64 for MIME bodies, PEM keys and most API payloads. Use URL-safe Base64 the moment the string will travel in a URL, a filename, a cookie or a JWT. If you are debugging a token, paste it into Decode and the tool will accept either alphabet, so a truncated or padded segment still resolves to readable JSON.

Questions

Frequently asked questions

What is Base64 encoding used for?

Base64 lets binary data travel through systems built for text. You will meet it in data URLs for inline images and fonts, MIME email attachments, JSON payloads that carry files, JWT segments, HTTP Basic Auth headers and PEM-encoded certificates. Anywhere a channel cannot accept raw bytes, Base64 is the standard bridge.

Is Base64 encryption?

No. Base64 is a reversible encoding with no key, so it provides no confidentiality at all — decoding it requires nothing but the string itself. Use it for transport, never for protection. If data must stay secret, use real encryption such as AES-GCM in transit and at rest.

Why does my Base64 string contain plus and slash signs?

Those are two of the 64 characters in the standard alphabet, alongside the equals sign used for padding. They are perfectly valid in a MIME body or a JSON field, but inside a URL they need percent-encoding. Switch on the URL-safe toggle and they become a hyphen and an underscore with the padding removed.

How much larger is Base64 than the original data?

Roughly 33%. Three bytes of input become four characters of output, and padding can add up to two more characters at the end. A 30 KB image becomes about a 40 KB data URI, which is why the byte counter matters when you decide whether to inline an asset.

Can I decode a Base64 image back into a file?

Yes. Decode the string to recover the bytes, or paste a full data URI into the decoder and the tool reads the MIME type and payload, returning the underlying content. For binary results, download the output and rename the file with the correct extension.

Does the tool work offline?

Yes. Once the page has loaded there are no further network requests, so you can switch off your connection and every feature keeps working. That is also the simplest way to prove to yourself that nothing you type or drop is being uploaded anywhere.

Is there any limit on input size?

No imposed limit. Large payloads are processed in chunks so the browser never hits an argument-length ceiling, and multi-megabyte files convert in a few milliseconds. The practical ceiling is your device's available memory, not the tool.
