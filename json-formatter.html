Why it matters

Why exact error location beats “unexpected token”

Every JSON parser in the world can tell you that something is wrong. Almost none of them tell you where. A browser console throws “Unexpected token } in JSON at position 2048”, and a server framework replies with a stack trace that points at its own middleware rather than your data. Position 2048 means nothing until somebody counts the newlines. On a minified single-line response, it means nothing at all.

ToolGuest converts that character offset into a human coordinate. It walks the source up to the reported position, counts the newlines, and derives a 1-based line and column number — the same way a compiler reports an error. The message reads “Invalid JSON (line 42, column 8) — Unexpected token }”, and line 42 column 8 is exactly where you look. On a payload of several thousand lines, that difference is the gap between a thirty-second fix and a thirty-minute hunt.

There is a second, quieter benefit: the parser's own message is preserved rather than replaced. V8's wording — “Unexpected token”, “Unexpected end of JSON input”, “Bad control character in string literal” — is precise once you know where to look, and stripping it would hide useful information. The tool shows the raw message and the coordinate together, so experienced engineers get the detail they want and newcomers get a location they can act on.

Developer notes

JSON habits that age well in production

Keep payloads valid, not merely parseable. JavaScript's JSON.parse is stricter than the JavaScript object literal syntax it resembles, which is why { a: 1 } works in a script but not in a .json file: keys must be double-quoted, strings must use double quotes, and no trailing comma is allowed. When a payload “works in code but fails in a file”, that mismatch is almost always the reason.

Treat formatting as part of the contract. A repository that commits formatted JSON with a fixed indent and sorted keys produces diffs a reviewer can actually read, and it removes the whole class of “whitespace-only” pull requests. Sort keys where order does not carry meaning, and leave arrays alone where it does — a list of steps is a sequence, not a set.

Finally, remember that JSON has no comments by design. If a config file needs explanation, keep it in a separate README or a companion schema rather than smuggling // into the data, where a strict parser will reject it. Validate before you commit, and let the tool tell you the exact line and column when something slips through.

Questions

Frequently asked questions

What is the difference between formatting and validating JSON?

Validating checks that the document conforms to the JSON standard and parses without error. Formatting (or beautifying) reprints a valid document with consistent indentation and line breaks so a human can read it. ToolGuest does both: validation runs on every keystroke, and the Format button pretty-prints the result.

How does it find the exact line and column of an error?

When JSON.parse fails, the V8 engine reports a character position such as “at position 42”. The tool counts the newlines up to that offset to derive a 1-based line and column number, then shows both alongside the parser's own message, so you can jump straight to the broken comma, quote or bracket.

Can it handle multi-megabyte JSON files?

Yes. Formatting and minifying run through the browser's native parser, which is far faster than hand-written JavaScript. Payloads of several megabytes render in milliseconds, and the practical ceiling is your machine's available memory rather than anything inside the tool.

What does the “Sort keys” option do?

It reorders object keys alphabetically at every level of the document, recursively. That makes diffs between two versions of a payload far easier to read and produces stable output for snapshots and tests. Arrays keep their original order, because element order is meaningful there.

Is my JSON uploaded anywhere?

No. The entire tool runs client-side in vanilla JavaScript. There is no upload endpoint, no logging and no analytics, which is why it is safe to paste internal API responses, unreleased fixtures or customer data. Turn off your network connection and the tool keeps working.

Does it support JSON Lines or NDJSON files?

Not directly, because each line of an NDJSON file is a separate JSON document rather than one valid document. Paste one line at a time to validate it, or wrap the lines in a JSON array and format the array in a single pass.

Why does my JSON say “invalid” when it looks perfectly fine?

The usual culprits are a trailing comma before a closing bracket, single quotes instead of double quotes, unquoted object keys, a stray // or /* */ comment, or a smart quote pasted from a word processor. The error bar shows the line and column where the parser gave up, which is normally a character or two after the real mistake.
