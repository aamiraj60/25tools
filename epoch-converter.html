Under the hood

How client-side epoch parsing actually works

No conversion endpoint. No query log. The date math runs on the same CPU that renders this page.

The arithmetic

A Unix timestamp is a count of seconds from the epoch. Converting it is one multiplication, because JavaScript’s Date constructor takes milliseconds. The whole decode is a single expression: 

new Date(1767225600 * 1000).toISOString();
// "2026-01-01T00:00:00.000Z"

The reverse direction parses an ISO 8601 string to an absolute instant and floors it back to whole seconds, which is exactly what a database column expects: 

Math.floor(Date.parse("2026-01-01T00:00:00Z") / 1000);
// 1767225600

Timezones without a timezone library

Every zone in the grid is rendered by the platform’s own internationalization API, so daylight-saving rules come from the browser’s tzdata rather than a bundled database that goes stale. Passing an IANA identifier is all it takes: 

new Intl.DateTimeFormat("en-GB", {
  timeZone: "Europe/Berlin",
  dateStyle: "medium", timeStyle: "long"
}).format(1767225600 * 1000);
// "1 Jan 2026, 01:00:00 CET"

That is why the same instant can legitimately be Tuesday in San Francisco and Wednesday in Berlin, and why the grid is more useful than a single “converted” value. Relative wording such as “3 hours ago” is produced the same way, through Intl.RelativeTimeFormat.

Epoch and timestamp questions, answered

A Unix epoch timestamp is the number of seconds elapsed since 00:00:00 UTC on 1 January 1970, ignoring leap seconds. Because it carries no timezone, it is the lowest common denominator every database, API and log format can agree on.

Count the digits. Ten digits (1767225600) is seconds and lands in a sensible year; thirteen digits (1767225600000) is milliseconds. JavaScript's Date.now() returns milliseconds, while most Unix tools and database columns store seconds — which is where the “year 55000” bug comes from.
